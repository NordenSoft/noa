## 1. Legend

Each surface gets **two** tables, because thirteen columns in one markdown table is unreadable and an unreadable control is not a control.

**Table (a) — AUTHORITY.** `F` field · `SIG` security significance · `SRC` original source · `AUTH` the principal *entitled* to determine it · `DERIV` derivation rule as implemented · `CI?` is caller input accepted today · `CLS` required provenance class.

**Table (b) — MECHANICS.** `F` field · `CANON` canonical representation · `PARSE` parse provenance (own key or inheritable? absence forgeable? duplicate-key behaviour?) · `READS` reads between authentication and consumption, and off which object · `GATE` which mechanical gate fires if this regresses · `MUT` the mutation test that would catch it · `FAIL` failure behaviour today.

### 1.1 Provenance classes A/B/C/D

`[reconstructed]` The owner's item-4 class definitions are **not written anywhere in this repository.** Reconstructed from the only two in-repo usages — `docs/GATE-PROVENANCE-FINDINGS-2026-07-30.md:189` ("class **(C)** — independently observed from an authenticated external authority") and `:212` ("unauthenticated, unversioned, pinned in no artifact. Class **(B)** demands the opposite"):

| Class | Meaning | Admissible source |
|---|---|---|
| **(A)** | Untrusted caller assertion. May be *recorded*; may never *decide*. | the caller |
| **(B)** | Trusted provisioned state. Must be authenticated at load, version-pinned, and committed in a signed artifact. | out-of-band provisioning + a root-signed manifest |
| **(C)** | Independently observed from an authenticated external authority. | a signature from a key the boundary trusts *for that purpose* |
| **(D)** | Derived by the trusted boundary itself, deterministically, from inputs that are already (B) or (C). | the boundary's own code |

> **OWNER DECISION 1 — confirm or correct this mapping.** Every `CLS` cell below depends on it. If the intended definitions differ, the classes are wrong but the rows, reads and citations remain valid.

### 1.2 The rule, and what makes a row BLOCKING

> **Any field that affects a trust decision without an authenticated provenance rule is a BLOCKING ARCHITECTURE DEFECT.**

Two distinct defect kinds are separated throughout, because they need different fixes and the previous analyses blurred them:

- **AUTHORITY defect** — the value is class (A) where (B), (C) or (D) is required. The read discipline may be perfect. `createHold`'s field capture is in fact clean: every field is read exactly once into a local. **It captures the wrong principal's word carefully.** Fix: change who is entitled to write it.
- **TEMPORAL defect** — the value has an admissible class *and* a real signature, and is still exploitable because the read that was **authenticated** and the read that is **consumed** are different reads of the same caller-owned object. Fix: parse to bytes once; never re-read.

`decisionArtifact.decision` is class (C) with a genuine Ed25519 signature over `DENY`. Its honest authority row is **GREEN**. It is M3. That is why the temporal column exists.

### 3.1 M7 — NEW CRITICAL. ENFORCED mode splits display from params with no caller display field at all.

`projections.ts` reads the caller's live `argv` array **three separate times**:

```
projections.ts:68   !argv.every((a) => typeof a === "string")   // read 1 — the type check
projections.ts:82   sha256Prefixed(canonicalize(snapshot))      // read 2 — becomes paramsHash
projections.ts:90   (argv as string[]).join(" ")                // read 3 — becomes display.Args
```

`:74` puts the **same array reference** into `snapshot`, not a copy. So `paramsHash` is derived from read 2 and the human's display text from read 3, and nothing constrains them to agree.

```console
$ node /tmp/arch-op2/m7b.mjs
status                         : 201  mode: ENFORCED
HUMAN IS ASKED TO APPROVE      : {"Action":"noa.command.exec","Command":"/bin/rm","Args":"--help","Cwd":"/srv","Env":"production"}
the signed paramsHash binds    : "/bin/rm -rf /srv"  <== DESTRUCTIVE
envelope attests displayProjection: noa.command.exec.display — i.e. it claims a reviewed renderer produced the text above

VERDICT: ENFORCED mode asked the human to approve `/bin/rm --help` and bound the grant to `/bin/rm -rf /srv`.
```

Anti-vacuity control, same run in `m7-argv-split.mjs`:

```
=== ANTI-VACUITY: an HONEST argv (no accessor) must agree ===
 honest createHold status      : 201
 honest paramsHash == mk('/srv/app')? true
 honest display shows          : /srv/app
 AGREE? yes — honest path is coherent, so the split above is the accessor's doing
```

**Why this outranks M1 as an argument.** M1 requires the caller to supply an `encryptedDisplay` field, so a fix can plausibly be framed as "stop accepting that field". M7 supplies **no display of any kind** — no `display`, no `encryptedDisplay`, no `paramsHash`. The pinned projection runs, is the sole author of both values, and still produces two that disagree. **The split is not in what the gate accepts; it is in how the gate derives.** Removing every caller display field, as ADR-0004 §3 proposed, does not close M7.

`Array.isArray(argv)` is `true` for an array with an accessor at index 0, so `:65`'s guard is passed honestly.

**Reachability:** requires defining a getter on an array index, which `JSON.parse` cannot produce — so the in-process client (`packages/gate/src/index.ts:31`, exported and supported) or an ambient dependency in the gate's realm. Same class as M3/M4. `[UNVERIFIED: reachability over HTTP — an array-index accessor cannot be expressed in JSON; I did not find an HTTP route to it and did not exhaust the search.]`

**Stated at the right strength, and not higher.** `packages/relay/src/engine.ts:1-19` documents the relay as untrusted transport whose trust is anchored at the consumer, and the gate does re-verify against its manifest keyring (`engine.ts:448-491`). **So R-1 is not a forged gate grant.** What it is:

1. **An authorization defect that stands on its own.** Anonymous callers minting agent credentials is not a trust-boundary question. `POST /v1/pairings` → `POST /v1/pair` is an open credential-issuance pipeline (`server.ts:167-176`).
2. **`custodyTier` is a self-asserted trust attribute** (`:162`). A field named for hardware custody, written by the party whose custody is in question, defaulting silently to `"software-browser"`.
3. **No tenant scoping anywhere in the relay.** `HoldRecord` (`types.ts`) has no tenant field. `listPending` `:383-395`, `getDisplay` `:361`, `getHoldContext` `:376` take **no device argument** and apply no per-hold or per-tenant scope: any registered device reads every hold's action metadata, sealed display blob and signed envelope. That is the remote harvesting primitive M5's cross-hold replay needs.
4. **`notify` `:719` pushes every hold to every device** (`listAllDevices()`), leaking `action.canonical` cross-tenant.
5. **`hold.status = APPROVED` / `reasonCode = HUMAN_APPROVED` is written by the relay** (`:444-445`) and returned to any consumer (`:703-704`). Any consumer that reads relay status instead of re-verifying inherits a forged approval. The relay's own docstring says not to; nothing enforces it.

**Two independent copies of `riskClass` exist and are never compared** — the relay's (shown to the human, `:388`) and the gate's (selects the approver tier, `verify.ts:260`). Neither is bound to the other or to any signature.

The control fires: with an envelope present the check works correctly. **Absence of the envelope disables it** — the same "an omission is not an absence of opinion" class the relay's own `putManifest` closed at `:506-514` for `delegation.tenant`, recurring 240 lines away in the same file.

### 13.3 Severity calibration — stated because I first stated it too strongly

**The relay is loopback-by-default and its bind guard is mechanical.** `packages/relay/src/config.ts:49-52`: `bindAddress: "127.0.0.1"`, `unsafeListen: false`, `tlsTerminated: false`; and `packages/relay/src/server.ts:62-73` **refuses to start** on a non-loopback address without *both* `unsafeListen` **and** `tlsTerminated`. The package is `"private": true` and no workflow deploys it.

**So R-1 and R-2 are not a live internet exposure today.** "No authentication at all" means *for anyone who can reach the port*, and on the default configuration that is the local host only.

**But the relay's stated purpose is to be reachable.** `packages/relay/package.json` describes it as *"a hosted, framework-free (node:http) transport"*, and hosting it means setting `unsafeListen: true` + `tlsTerminated: true` — at which point `POST /v1/pairings` → `POST /v1/pair` becomes an **internet-facing anonymous credential-issuance pipeline**, and `listPending`/`getDisplay`/`getHoldContext` become internet-facing unscoped reads.

**Correct classification: a pre-deployment blocker, not an incident.** That is a more useful statement than "critical remote hole", and it is the one the evidence supports. It also means the fix has no urgency-driven excuse for being partial: there is no live traffic to preserve compatibility with, and per this project's own memory production currently holds zero tenants.

## 16. What this matrix cannot represent, and why that is the finding

A field × provenance-class matrix **cannot express M3, M4 or M7**:

- **M3** — `decisionArtifact.decision` is class (C) with a real approver signature over `DENY`. Its authority row is GREEN and the field is exploitable. The defect is in the *pair* `(value, read)`, not the field.
- **M4** — `encryptedDisplay`'s **absence** is the exploited quantity. Absence has no field to put in a row.
- **M7** — every input is honest, the authority is correct, the pinned projection is the sole author of both outputs, and it derives them from **two different reads** of one array.

> **Provenance is a property of a `(value, read)` pair, not of a field.** A value re-read from a mutable object after its authentication has no provenance, whatever its origin. And a value read *twice by the boundary itself* has no single provenance even when the caller never touches it in between.

That is the invariant ADR-0005 is built on, and it is why the fix is a **parse boundary plus a read discipline**, not more fields in more digests. Adding `riskClass` to `paramsHash` makes M2 tamper-evident and leaves it exploitable. Deleting every caller display field closes M1 and leaves M7 open.

## 17. Owner decisions this matrix requires

1. **Confirm the A/B/C/D definitions** in §1.1. They are reconstructed from two in-repo usages; the authoritative text is not in the repository. Every `CLS` cell depends on them.
2. **`riskClass` — (D) derived or (B) provisioned?** Deriving it from `(canonical, params)` needs a per-action-type rule in the registry; provisioning it needs the projection manifest of §39. Both close M2; they differ in operational cost.
3. **`mode` — delete `RAW`, or make it a provisioned per-agent capability?** RAW is the branch where `display` and `paramsHash` are independent caller inputs. NC-6.6's ratified consequence already says RAW "**must not** issue a `HUMAN_APPROVED` grant or approval receipt for a critical action". Deleting RAW is simpler and breaks any existing RAW integration.
4. **Relay authority model.** `POST /v1/pairings`, `/v1/pair` and `/v1/devices` are open routes and the relay has no tenant field at all. This is a scope decision, not a patch: does the relay become tenant-scoped with authenticated device enrolment, or does it stay a pure blind transport that publishes **no** status field a consumer could mistake for an approval?
5. **`packages/relay/src/` gate coverage.** 2,552 lines, zero mechanical coverage. Extending `scripts/lint-security-gates.mjs` past `walk("src")` is the single highest-leverage change in this document and it will surface unclassified files across five packages at once.
6. **M7 severity and sequencing.** It is CRITICAL and it is *not* closed by any fix proposed in ADR-0003 or ADR-0004. It should gate Stage 1 alongside M1–M6.
